### Deviations from the plan/spec
  * Store defaults hooks.postMigrate to runPostMigrate (plan listed it as an injected hook only); passing null disables it. Chosen so a composition root that forgets the hook cannot leave semantic_key NULL after an upgrade.
  * runPostMigrate rejects DreamWorker template candidates BEFORE backfilling semantic keys (plan listed backfill first). Rejected templates are therefore never keyed and cannot trigger spurious merge proposals. Report gains an `alreadyApplied` boolean on top of the three plan fields.
  * verifySqliteHeader also treats files shorter than 100 bytes (incl. 0-byte files) as damaged, and the store additionally runs PRAGMA quick_check(1) at load time (spec §9.4 F1 names header and quick_check as recovery triggers; the plan text mentioned only the header).
  * A non-noop WriteOp whose id is already in write_ops is not an error: the store rolls the callback's changes back and reports {op.noop: true, alreadyApplied: true} instead of letting the write_ops PRIMARY KEY insert throw (plan: 'same id second time -> noop').
  * runMigrations(dbPath) now returns RunMigrationsResult (was Promise<void>) and accepts either an options object or the legacy console-like logger; it stays lock-free as before (hm db:migrate should use Store.withWriteLock, which performs the same steps under locks/db.lock).
  * renameWithRetry also treats EACCES like EPERM/EBUSY for the copy fallback (libuv maps some Windows sharing violations to EACCES).
  * test/migrator.test.ts no longer uses MemoryRepository.create/update (A2 is changing that API concurrently); it verifies post-upgrade writability with raw SQL and asserts the renamed legacy_* tables, so it stays green independent of A2's work.

### Deviations from the plan/spec
  * Duplicate detection in create(): a live twin by identity_key OR semantic_key throws; a shared content_hash alone does NOT (the plan's A2 bullet said 'identity_key or content_hash'). Rationale: spec §4.1/§5.7 make scope part of a fact's identity (semantic_key = type|scope|signature|summary), the same text in a different scope is a different fact, and the existing test 'allows same text when scope differs' encodes that; `getByContentHash(hash, {live})` remains for callers that want the stricter check.
  * Terminal twins without `reviveTerminal` throw DuplicateMemoryContentError(matchedBy 'terminal_twin') instead of attempting an INSERT whose deterministic id would violate the primary key (the plan only specified the reviveTerminal=true path).
  * AuthorityViolationError is raised for ANY transition attempted by auto_rule/expiry on an authority='human' row (spec §4.7 '상태를 불문하고 엄격하다'), not only for demotions as the plan phrased it; in practice identical because every auto_rule/expiry edge in the table is auto-only.
  * create() computes semantic_key by default (spec places the computation in reconcile step 2; the value is identical since both use core/ids.semanticKey); `semanticKey: null` opts out for merge-proposal losers.
  * transitionMemory additionally writes the compatibility column promotion_source ('manual' on human promote/restore, 'auto' on auto_rule promote, per §7.4) and last_verified_at = now on every → active edge; setAuthority(id,'human') also clears ttl_expires_at/revalidate_after and sets promotion_source='manual' (spec §7.1: human rows carry no TTL).
  * revalidateMemory also accepts auto rows in status `stale` (so reconcile can revalidate a ttl_expired row before reactivating it) and leaves the stale→active transition to the caller; revalidate_after moves to max(existing, midpoint(now, ttl)) — the plan did not specify revalidate_after on reinforce.
  * isAllowedTransition takes an optional 5th argument `{ statusReason }`; the stale→active/auto_rule edge is gated on status_reason='ttl_expired' only when the reason is supplied (transitionMemory always supplies it) so the pure table check stays usable without a row.
  * The §4.7 status-write grep invariant test excludes src/db/post-migrate.ts in addition to transitions.ts, migrations/ and db/repositories/ (the plan explicitly lets post-migrate bypass transitionMemory).
  * ProposalRepository orders ties by rowid (insertion order) instead of id because proposal ids are random UUIDs; EpisodeRepository treats `flags.correction = 1` OR `correction_for IS NOT NULL` as a correction episode for lease ordering and the daily-cap exclusion.
  * rejectMemory/mergeMemories/supersedeMemory/markMemoryStale were removed from MemoryRepository rather than rewired to transitionMemory (spec §4.7 wording): rewiring would create a memory→promotion→memory import cycle and their only callers were the retired CLI/dream modules; CLI equivalents are one transitionMemory call.

### Deviations from the plan/spec
  * signature_key appends `|!` when `negate` is true (plan format `tool|target|kind|canonical pattern` has no negate slot; without it a negated and a non-negated signature would collide on semantic_key). parseSignatureKey/compileSignatureKey understand both forms.
  * §4.6 grammar implemented as a superset: besides `npx|pnpm dlx|bunx`, `yarn dlx`, `bun x`, `npm exec|x` and `pnpm exec` also fold to `bin <bin>`; npm script aliases `t|tst → test`, `i|in|ins|inst|insta|instal|isnt|isnta|isntal|isntall → install`; a bin `@version` suffix is stripped; the program token is the lower-cased basename with .exe/.cmd/.bat removed. `run`/`run-script` is dropped only when it is the first non-flag token after the package manager.
  * primaryProgramToken (the value hooks should store as `program_token` / use in failure_sig) skips leading shell-navigation segments (`cd x && npm test` → `pm test`) instead of taking the literal first canonical token as §5.1 reads; canonicalizeCommand().programTokens still exposes every segment's token.
  * V8 restatement is implemented as: normalized summary is a substring of the normalized prompt, OR the summary has ≥ 8 distinct tokens with ≥ 80 % of them present in the prompt. The plan's bare 80 % overlap rule rejected legitimate normalized facts extracted from short prompts (e.g. 'Run pnpm test instead of npm test' vs the user's one-line correction).
  * Import-mode citation (V4) accepts a canonical cmd citation in addition to the verbatim quote the spec requires, so a `pm test` pattern is cited by a bullet that says `npm test`.
  * V6 self-reference is implemented inside validate.ts (the spec lists a separate security/self-reference.ts, outside A3's files); the scanner is called with the current 3-arg signature, without the `{source: 'extraction'}` option the spec mentions (not yet present in ScanOptions).
  * §9.3 B: a same-tool, same-signature `tool_fail` immediately after a soft_deny fired line is classified `none` (the warning was right); the spec only defines tool_ok → override and another tool call → heed. Non-soft_deny fired lines (advise/confirm/deny) are always `none`.
  * decideTier returns additional reasons `'scope' | 'trigger' | 'security'` beyond the plan's union, and shadow autonomy is reported as {status: 'candidate', reason: 'autonomy', shadow: 'active'} rather than a separate return shape; policy rows get their activate_policy proposal even when autonomy_level is 'off'.
  * parseExtractionOutput clips over-long text (summary > 160, details > 1200, rationale > 300, episode_summary > 400) and tolerates a missing `nothing_to_learn` / `aliases` instead of rejecting the whole output; wrong types, enums, missing citations and malformed signatures still reject the fact (V1).
  * The extraction prompt renders a compact field list under `# Output` instead of the verbatim JSON schema text (the provider receives the schema through --json-schema / --output-schema); the `aliases` field (added by core beyond the spec's §5.5 schema) is included in the instructions.
  * minimatch is loaded lazily through createRequire inside compileGlobSource rather than imported statically as the plan's `minimatch.makeRe(...)` wording suggests, so hooks that only call matchSignature honour the 'hooks never import minimatch' convention.
