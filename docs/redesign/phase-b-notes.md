### Open issues
  * Dense leg timing: the client default is the planned 30 ms; a warm multilingual-e5-small forward pass on CPU is typically 10–40 ms, so the dense list may frequently arrive late (treated as null → lexical only, no error). Dense is off by default (embeddings.enabled false). Dogfood should measure and, if needed, expose the timeout in config (before_model.dense_timeout_ms) — a one-line change in createRuntime/createDenseClient.
  * Lexical recall depends on B1 adopting lexicalSnapshotOptions() + the tokenizer stamp (see cross-module request); until then identifiers and Korean inflections match only when spelled exactly as indexed.
  * Recursion guard 2 (worker.pid ppid chain) is implemented for POSIX via /proc only and is a documented no-op on Windows; guard 1 (HARNESS_MEMORY_DISABLE=1 from providerEnv) covers nested `claude -p` on every platform.
  * Stop/PreCompact/SessionEnd skip writing an episode when the segment holds only assistant/marker lines (status skipped:empty_segment, state untouched). This avoids junk queue files on every continued Stop; the next close includes those lines.
  * `before_model` is once per user turn only because UserPromptSubmit fires once per prompt; there is no ledger-side guard against a host that fires it twice.
  * The stale-snapshot check uses a 1 ms mtime tolerance against snapshot.source; if B1 stats the DB before its final rename (see request) every hook would see 'stale' and spawn one throttled reindex per minute.
  * hook-core sweeps idle turns at session-start in parallel with B1's consolidate sweep; both produce the same deterministic episode ids, so the worker's INSERT OR IGNORE dedupes, but the consolidate test suite should tolerate pre-existing queue files.
  * No end-to-end test spawns `dist/hook.js` (no `npm run build` per the brief); the import-graph test guards the no-sql.js/minimatch/transformers rule statically, and B3's build + eval:latency cover the bundled path.

### Deviations from the plan/spec
  * `permissionDecision` is never 'allow' (would auto-approve the user's own permission prompts); advise rows emit additionalContext only and HookResult.decision is 'none' (HookDecision 'allow' is unused by the hooks).
  * A `fired` ledger line is appended only when at least one memory or rule fired (spec §6.2 step 10 reads as unconditional); delivery 'none' therefore never appears on a fired line.
  * before_model's BM25 threshold is applied to the normalized score s/(s+1) (default min_score 0.35 ≈ raw BM25 0.54) so the config value lives on a 0–1 scale comparable to the dense cosine threshold (0.80); the plan said 'BM25 ≥ min_score'.
  * session_start requires `lifecycle_triggers ∋ session_start` for baseline rows too (spec §6.1 'rows whose lifecycle_triggers contain session_start'); v0.5 baseline rows that lack the trigger are no longer dumped at startup until a writer adds it.
  * Korean particle stripping (`stripHangulParticles`, up to two trailing particles, stem ≥ 2 syllables, stem + original emitted) was added to the snapshot tokenizer for alias recall; the spec only asks for aliases to be indexed. The in-DB LexicalIndex keeps the previous tokenizer unchanged.
  * Stop with `stop_hook_active` still closes the segment as the spec demands, but a segment containing no prompt/tool_*/fired line is skipped (no queue file, state untouched) instead of producing an empty episode.
  * after_tool hints are produced only on PostToolUseFailure (there is no failure class on a successful PostToolUse); PostToolUse still writes the tool_ok line and resolution_of.
  * The prompt hook stores the previous episode's byte range in the new SessionState.last_episode_range so the stop hook can render the corrected episode's tool lines into context_ref without re-reading the queue file (which the worker may already have consumed).
  * `hook-launch.ts` calls `enableCompileCache` through `import * as nodeModule from 'node:module'` and loads the bundle through a variable import specifier and `main(argv)` (the spec's `require('./hook-bundle.js')` is not available in an ESM launcher and a literal specifier cannot be resolved by tsc/esbuild at build time).
  * src/policy/types.ts and src/policy/repository.ts were edited although only src/policy/engine.ts was in my file list (additive 020 columns + enforcement on PolicyWarning); the §10 rewrite is impossible without them and no Phase B engineer owns them.
  * Three small core additions beyond my file list: SessionState.last_episode_range, LexicalSnapshot.tokenizer?, and findInstalledRoot/findProjectRoot excluding the user-level ~/.harness-memory (a real bug on this machine: ~/.harness-memory exists, so any project under the home directory would otherwise resolve to it).
  * readStdin resolves with an empty string on a TTY instead of waiting for the timeout (manual invocations of dist/hook.js return `{}` immediately).
  * The embedding helper probes a pre-existing POSIX socket with a 200 ms ping before unlinking it and exits 0 on EADDRINUSE (spec said only 'remove a stale socket file').

  * Live `claude -p` / `codex exec` were not exercised (m0-facts #3: the CLI on this machine is not logged in; codex is not installed). classifyClaudeRun covers the documented envelope and the observed not_logged_in text; the nested-refusal wording is a regex guess (/nested|inside … claude|CLAUDECODE|cannot … within/i) and the codex `--json` event shape is parsed tolerantly (last message text, else whole stdout). Both need a dogfood run with a logged-in CLI.
  * `--tools ""` + `--json-schema` coexistence is still unverified (m0 open item); a probe returning `invalid_output` is surfaced as RunStatus invalid_output and cached daily, so `doctor` can show it.
  * Probe cache and provider-unavailable requeue both use a 24 h window, so an episode that waited on a failed probe becomes due at the same moment the cache expires; the next worker run re-probes once and then processes everything — intended, but it means a persistently not-logged-in install re-probes exactly once a day per worker spawn.
  * runDream is not wired to a `stop` hook trigger ("6 h since last_dream_at") — that scheduling decision belongs to the hooks (B2) using snapshot.last_dream_at; the worker only exposes the `dream` command.
  * Reconcile's neighbour search runs Jaccard over all live memories of the fact's type per fact (O(n) per fact); fine for the v1 sizes (≤ a few thousand rows) but not indexed.
  * Idle sweep semantics (segment reset to 0, marker line appended, correction_for dropped) were chosen without B2's final state-file code; see cross_module_requests. The `last_episode_range` field B2 added to SessionState is not populated by the sweep yet.
  * Snapshot `counts.active` counts the rows included in the snapshot (unreachable rows excluded); `doctor`/`status` wanting the raw DB count should use MemoryRepository.countByStatus().
  * Embedding backfill in dream only runs when a caller injects `embed` (src/worker.ts passes none); wiring @xenova/transformers into the worker is left to B3/B2 (EmbedFn = (texts) => Promise<Float32Array[]>).

### Deviations from the plan/spec
  * §5.8 step order: fire-based TTL extension and the override downgrade (listed as step 4) run before the TTL check (step 2) so a row that fired recently is extended instead of expired/proposed for revalidation; otherwise step 2 would stale rows that step 4 is about to mark 'in use'.
  * §9.4 F3 backoff: attempts fail with backoff 1 h (after attempt 1) and 6 h (after attempt 2); the third failed attempt makes the episode `dead` ("3회 후 dead"). The spec's third backoff value (24 h) is used for the provider-unavailable statuses (no_provider / not_logged_in / nested_refusal), which per m0-facts #3 keep the episode `queued` without consuming an attempt (next_attempt_at = now + 24 h).
  * §9.3 E: queue files are deleted right after lock session 1 commits (the episode row exists, INSERT OR IGNORE makes a re-read harmless) instead of after lock session 2; a crash between B and D leaves the episode leased → requeued after 180 s with no file to re-read.
  * §5.7 step 1: a re-applied run also marks the episode `extracted` when it is not yet (noop + wrote) exactly as the plan says; additionally the Store's own alreadyApplied check is bypassed by returning noop ourselves, so the store never sees a non-noop op for an applied run.
  * §5.7 step 6: `open_proposal_id`/`contested` are set on auto targets too (not only human ones) so the CLI/status see every open proposal; the injection-text marker rule (human advise rows with ≥ 2 support sessions) stays the hooks' decision. Proposal rationale carries fix_scope/fix_signature payloads as a `\n@payload <json>` suffix (the schema has no payload column).
  * §4.8: rows whose stored signature no longer compiles are not automatically unreachable — the signature is dropped and the row stays in the snapshot when another trigger (or scope-only pitfall/policy before_tool) still reaches it; they are listed in SnapshotBuildResult.signatureDropped and `worker dream` opens a `fix_signature` proposal for them. counts.expiring_7d adds auto rows whose TTL ends within 7 d to the proposals expiring within 7 d.
  * Import-host reconciliation (not fully specified for B1): facts from host 'import' episodes become human/import rows that are `active` with import_unconfirmed = 1 (enforcement advise) so `hm import --yes` works through the worker; the confirmation table (C1) clears the flag.
  * Session summaries are written with raw SQL (deterministic id, injected `now`) instead of SummaryRepository, whose timestamps use the wall clock; the medium summary accumulates the last episode summaries (≤ 2000 chars) rather than mirroring the short one.
  * The probe result of the replay provider is never cached in meta (its 'ok' would mask a real provider's failure in `status`); selectProvider honours the HARNESS_MEMORY_PROVIDER environment override (already allowlisted by providerEnv) ahead of config.extraction.provider so eval:replay can force the replay provider.
